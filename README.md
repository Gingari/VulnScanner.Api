# Vulnerability Tracker API

**REST API на C# / ASP.NET Core 10 для регистрации уязвимостей и фонового анализа Git-репозиториев.**

Автор: **Гапон Е.А.**  
Репозиторий: [Gingari/VulnScanner.Api](https://github.com/Gingari/VulnScanner.Api)

Сервис принимает ссылку на публичный репозиторий, помещает задачу в ограниченную очередь и запускает Gitleaks и Trivy. Клиент сразу получает ID задачи, а затем запрашивает её состояние и результат. Ожидающую или выполняющуюся задачу можно отменить.

> **Состояние только в памяти.** Уязвимости, задачи, результаты и очередь исчезают после перезапуска. Кеш базы Trivy в Docker volume — технический кеш, а не постоянное хранилище состояния API.

## Возможности

- Ручное добавление уязвимости с названием и критичностью, автоматическими ID и датой.
- Получение полной записи об уязвимости по ID.
- Асинхронное сканирование репозиториев с немедленным ответом `202 Accepted`.
- Ограниченная очередь и настраиваемое число параллельных задач.
- Статус задачи, время последнего изменения и единый результат анализа.
- Отмена в очереди и во время выполнения, с передачей сигнала внешним процессам.
- Централизованные ошибки в формате Problem Details и логирование HTTP-запросов.
- Swagger UI и OpenAPI; unit- и интеграционные HTTP-тесты.

### Анализаторы

| Инструмент | Что проверяет | Особенности |
|---|---|---|
| Gitleaks | Потенциальные секреты в текущих файлах | История Git не анализируется; значения секретов не включаются в модель результата |
| Trivy | Известные уязвимости распознанных зависимостей | Используется `fs --scanners vuln`; база уязвимостей загружается/обновляется инструментом |

Анализаторы выполняются последовательно над одной скачанной копией. Наличие находок — успешный результат анализа, а не ошибка исполнения.

## Быстрый запуск в Docker

### Требования

- Docker Engine или Docker Desktop с **Linux containers**.
- Docker Compose v2: команда `docker compose`.
- Интернет для сборки образа, клонирования и загрузки базы Trivy.
- Для подготовленного Dockerfile — Linux x64 / обычный ПК Intel или AMD. Под ARM64 потребуется адаптировать загрузку бинарников.

Проверка:

```powershell
docker version
docker compose version
```

### Запуск

```powershell
git clone https://github.com/Gingari/VulnScanner.Api.git
cd VulnScanner.Api
Copy-Item .env.example .env
```

На Linux/macOS вместо `Copy-Item`:

```bash
cp .env.example .env
```

**Перед сборкой укажите в `.env` реальные проверенные версии `GITLEAKS_VERSION` и `TRIVY_VERSION`, без префикса `v`.** Пустые значения намеренно не выбирают случайную версию инструмента. Если инструменты уже установлены, версии показывают `gitleaks version` и `trivy --version`.

Далее:

```powershell
docker compose up --build -d
docker compose logs -f api
```

С настройками примера:

- Swagger UI: **http://localhost:8080/swagger**
- OpenAPI JSON: **http://localhost:8080/swagger/v1/swagger.json**
- API: **http://localhost:8080/v1**

`Ctrl+C` прекращает просмотр логов, но не останавливает контейнер, запущенный с `-d`.

> Для Docker-запуска в корне репозитория должны находиться `Dockerfile`, `.dockerignore` и `compose.yaml`. Документация описывает согласованную конфигурацию Compose с сервисом `api`; отсутствие этих файлов нельзя исправить одним `.env`.

### Изменение настроек

Измените `.env`, например:

```dotenv
API_PORT=9090
Scanning__MaxParallelScans=2
Scanning__QueueCapacity=20
```

Примените:

```powershell
docker compose up -d
```

Swagger станет доступен на `http://localhost:9090/swagger`. Обычное изменение runtime-настроек не требует пересборки образа, но требует пересоздания контейнера. **Все задачи и записи при этом теряются.** `docker compose restart` не подхватывает новые переменные окружения контейнера.

Изменение кода, состава или версий инструментов требует сборки:

```powershell
docker compose up --build -d
```

### Остановка

```powershell
docker compose down
```

Кеш Trivy остаётся в именованном volume. Чтобы удалить и его:

```powershell
docker compose down -v
```

Следующее сканирование заново загрузит базу. Команда удаляет все volumes данного Compose-проекта — используйте осознанно.

## Локальный запуск

Требуются **.NET SDK 10, Git, Gitleaks и Trivy**, доступные из того же терминала, из которого запускается API:

```powershell
dotnet --version
git --version
gitleaks version
trivy --version
```

Официальные инструкции: [.NET](https://dotnet.microsoft.com/download/dotnet/10.0), [Git](https://git-scm.com/downloads), [Gitleaks](https://github.com/gitleaks/gitleaks/releases), [Trivy](https://trivy.dev/docs/latest/getting-started/installation).

Из корня проекта:

```powershell
Copy-Item .env.example .env
dotnet restore VulnScanner.csproj
dotnet run --project VulnScanner.csproj --launch-profile http
```

Профиль `http` из `Properties/launchSettings.json` использует:

- API: `http://localhost:5096`
- Swagger: `http://localhost:5096/swagger`

**`API_PORT` — переменная Docker Compose, не настройка локального Kestrel.** Чтобы локально выбрать другой порт:

```powershell
$env:ASPNETCORE_ENVIRONMENT = "Development"
dotnet run --project VulnScanner.csproj --no-launch-profile --urls http://localhost:9090
```

Локально `.env` загружается библиотекой DotNetEnv до создания `builder`. Запускайте из корня проекта. Благодаря `NoClobber()` уже существующие переменные процесса имеют приоритет над значениями `.env`.

## Конфигурация

ASP.NET Core использует двойное подчёркивание как разделитель секций: `Scanning__QueueCapacity` соответствует `Scanning:QueueCapacity`.

| Переменная | Пример / значение по умолчанию | Назначение |
|---|---|---|
| `API_PORT` | `8080` в Compose | Внешний порт компьютера; внутренний HTTP-порт контейнера — `8080` |
| `ASPNETCORE_ENVIRONMENT` | `Development` в примере | В этом окружении подключаются Swagger UI и OpenAPI |
| `Scanning__MaxParallelScans` | `2` | Максимум одновременно обрабатываемых задач, больше нуля |
| `Scanning__QueueCapacity` | `10` | Вместимость очереди ожидающих ID, больше нуля |
| `Repositories__AllowedHosts__0` … | `github.com`, `gitlab.com`, `bitbucket.org` | Разрешённые DNS-имена без схемы и пути; индексы с нуля |
| `Repositories__CloneTimeoutSeconds` | `120` | Тайм-аут запуска Git при клонировании, в секундах |
| `Repositories__TemporaryDirectory` | `<системный TEMP>/vuln-scanner` | Корень каталогов скачанных репозиториев |
| `GITLEAKS_VERSION` | Обязательная выбранная версия | Build argument для Docker; не меняет установленный локальный Gitleaks |
| `TRIVY_VERSION` | Обязательная выбранная версия | Build argument для Docker; не меняет установленный локальный Trivy |

Разрешённые хосты должны образовывать непустой список. Критичные значения проверяются при старте; некорректная конфигурация приводит к `OptionsValidationException`.

Переменные окружения приложения перекрывают одноимённые значения `appsettings.json`. В Compose явный блок `environment` имеет приоритет над `env_file`, поэтому не задавайте одну настройку в двух местах без необходимости. `API_PORT` и версии инструментов Compose использует также для подстановки в YAML.

### Что пока не вынесено в `.env`

Не все параметры динамические. В текущем коде зафиксированы:

- Gitleaks: до 2 минут выполнения; JSON-отчёт до 10 МиБ перед чтением.
- Trivy: CLI-тайм-аут 5 минут, внешний тайм-аут процесса 6 минут; JSON-отчёт до 20 МиБ перед чтением.
- ProcessRunner: до 64 000 символов сохранённого вывода на каждый поток stdout/stderr.
- Очерёдность анализаторов определяется регистрацией в DI.

Изменение этих значений требует изменения кода и пересборки. Общий deadline задачи, включая очередь и ожидание доступа к Trivy, не реализован.

## API

| Метод | Маршрут | Успешный ответ |
|---|---|---|
| POST | `/v1/vulnerabilities` | `201 Created`, ID и `Location` |
| GET | `/v1/vulnerabilities/{id}` | `200 OK`, полная запись |
| POST | `/v1/scans` | `202 Accepted`, ID и `Location` |
| GET | `/v1/scans/{id}` | `200 OK`, состояние и результат |
| POST | `/v1/scans/{id}/cancel` | `200 OK`, ID, время и подтверждение запроса отмены |

Подробные JSON-примеры, ошибки и переходы состояний: **[docs/API.md](docs/API.md)**.

### Быстрый пример в PowerShell

```powershell
$base = "http://localhost:8080"

$job = Invoke-RestMethod -Method Post `
    -Uri "$base/v1/scans" `
    -ContentType "application/json" `
    -Body (@{
        repositoryUrl = "https://github.com/Gingari/VulnScanner.Api"
    } | ConvertTo-Json)

Invoke-RestMethod -Uri "$base/v1/scans/$($job.id)"
```

Повторяйте GET, пока задача не перейдёт в `Completed`, `Failed` или `Cancelled`. Успешный HTTP-ответ POST означает принятие задачи, а не успешное клонирование или завершение анализа.

## Архитектура и параллельность

```text
HTTP → Controller → Service → In-memory repository
                        │
                        └── ограниченная очередь Channel<Guid>
                                      │
                           один ScanBackgroundService
                           ├── Worker 1
                           └── Worker N
                                      │
                              ScanOrchestrator
                              ├── Git clone (один раз)
                              ├── Gitleaks
                              ├── Trivy
                              ├── общий ScanResult
                              └── очистка каталога
```

- `MaxParallelScans` задаёт число worker-циклов, а не экземпляров API или отдельных потоков.
- Worker занят задачей до её завершения, включая ожидание Trivy.
- Адаптеры анализаторов — singleton-объекты; каждый запуск CLI — отдельный процесс. Данные конкретного вызова хранятся в локальных переменных.
- Внутри задачи анализаторы запускаются последовательно. В текущем адаптере Trivy дополнительно стоит `SemaphoreSlim(1, 1)`: одновременно выполняется один Trivy на экземпляр приложения.
- При полной очереди новый запрос получает `429`, запись и источник отмены откатываются.
- Отменённый в очереди ID физически остаётся в Channel до чтения worker. Поэтому его место может освобождаться не мгновенно.
- Запрос отмены и запись конечного состояния согласованы через `lock` конкретной задачи. Кто первым захватил блокировку, тот первым фиксирует переход.

### Основные каталоги

```text
API/            Контроллеры, HTTP-контракты, middleware, исключения
Analyzer/       Git-загрузчик, запуск процессов, адаптеры и оркестратор
Models/         Уязвимости, задачи, результаты, статусы и находки
Repositories/   Хранилища в памяти
Services/       Сценарии, очередь, источники отмены, BackgroundService
Options/        Типизированная конфигурация
tests/          Unit- и интеграционные тесты
docs/           API, эксплуатация и расширение анализаторов
```

## Тестирование

Для автоматических тестов нужен .NET SDK 10. Установленные Git, Gitleaks, Trivy, Docker и доступ к репозиториям не нужны: внешние зависимости заменяются тестовыми реализациями. При первом restore нужен доступ к NuGet либо готовый кеш пакетов.

```powershell
dotnet test ./tests/VulnScanner.Tests/VulnScanner.Tests.csproj
```

Примеры фильтров:

```powershell
dotnet test ./tests/VulnScanner.Tests/VulnScanner.Tests.csproj --filter FullyQualifiedName~TrivyScannerTests
dotnet test ./tests/VulnScanner.Tests/VulnScanner.Tests.csproj --filter FullyQualifiedName~ApiEndpointsTests
```

Покрытие:

```powershell
dotnet test ./tests/VulnScanner.Tests/VulnScanner.Tests.csproj --collect:"XPlat Code Coverage"
```

Отчёты создаются в `TestResults` тестового проекта. Конкретный процент покрытия не гарантируется и должен измеряться запуском.

Проверяются адаптеры и преобразование JSON, ошибки и очистка, объединение результатов, фоновое выполнение, отмена, параллельность и ограничение очереди. HTTP-тесты используют `WebApplicationFactory`: реальные маршруты и middleware работают в памяти, фоновые запуски отключены для повторяемости.

**Тесты с поддельным JSON не заменяют smoke-тест реальных инструментов.** Перед сдачей проверьте анализ на безопасном контролируемом примере с ожидаемой находкой, отмену настоящего процесса и очистку файлов. Не используйте реальные секреты.

## Безопасность и ограничения

Проект — тестовое решение, не production-ready платформа безопасного исполнения.

- Принимаются публичные HTTPS-репозитории точного разрешённого хоста, порт `443`, без credentials, query и fragment. Git-перенаправления отключены.
- Входной репозиторий не собирается, его зависимости и скрипты не запускаются. Submodules автоматически не скачиваются.
- Сканируется shallow-копия одной ветки с глубиной 1. Полная история, дополнительные ветки и содержимое submodules не анализируются.
- Приложение задаёт собственные конфигурации/ignore-файлы анализаторов; не доверяет предоставленной репозиторием конфигурации анализа.
- Значения `Secret`/`Match` Gitleaks не попадают в модель API; тела HTTP-запросов не записываются нашим middleware. Не передавайте секреты и токены в URL.
- HTTP-allowlist не заменяет сетевой egress-контроль и не является полной SSRF-защитой. Сетевая изоляция worker не реализована.
- API и анализаторы работают в одном процессе-хосте/контейнере, а не в отдельных изолированных worker-контейнерах. Безопасность анализируемого репозитория не гарантируется.
- Нет аутентификации, TLS-терминации, rate limiting по клиентам и квот на число завершённых записей. Не публикуйте API напрямую в интернет.
- Нет постоянного состояния и распределённой очереди. Несколько экземпляров API не разделяют задачи и результаты.
- Завершённые задачи остаются в памяти до перезапуска; большой поток задач/находок может исчерпать память.
- Ограничение размера JSON проверяется после его записи. Оно не ограничивает расход диска во время сканирования; временный диск ограничивается отдельно в Compose.
- Успешный анализ с нулём находок не доказывает отсутствие уязвимостей. Trivy должен распознать поддерживаемый manifest/lock-файл; один `.csproj` не гарантирует обнаружения зависимостей. API не выполняет `restore` недоверенного проекта ради получения таких файлов.
- Severity находок Gitleaks сейчас назначается политикой адаптера: `High`. Это не оценка, вычисленная Gitleaks.
- При ошибке любого анализатора задача получает `Failed`; частичные результаты клиенту не выдаются, повторов автоматически нет.
- Статус `TimedOut` объявлен в enum, но текущий фоновый обработчик относит исключение тайм-аута к `Failed`.
- GET возвращает изменяемую модель задачи, а не атомарный snapshot всех полей. Для production потребуется отдельный согласованный DTO-снимок.

## Перед сдачей

1. Указать проверенные версии инструментов в `.env.example`.
2. Добавить Dockerfile, `.dockerignore`, `compose.yaml`, документацию и тесты в Git.
3. Не коммитить `.env`, `bin`, `obj`, реальные ключи и скачанные репозитории.
4. Выполнить `dotnet test` и smoke-тест из чистого клона по этому README.
5. Опубликовать изменения на GitHub и проверить доступность репозитория.
6. Приложить файл `ГапонЕ.А_Тестовое задание_DevC#.txt` со ссылкой на репозиторий.
