# Эксплуатация и диагностика

[← README](../README.md)

## Где находятся данные

| Что | Локальный запуск | Docker-конфигурация проекта |
|---|---|---|
| Уязвимости, задачи, статусы и результаты | Память процесса | Память процесса контейнера |
| Скачанные репозитории | `<TEMP>/vuln-scanner/<scanId>-<randomId>` или `Repositories__TemporaryDirectory` | `/work/tmp/vuln-scanner/...` |
| JSON-отчёты и временные конфиги | `<TEMP>/vuln-scanner-reports/<randomId>` | `/work/tmp/vuln-scanner-reports/...` |
| База/кеш Trivy | Системный кеш самого Trivy | `/work/cache`, volume `trivy-cache` |
| Логи | Консоль | stdout/stderr, `docker compose logs` |

В Windows `<TEMP>` обычно открывается через `%TEMP%`. `Path.GetTempPath()` зависит от окружения; Dockerfile задаёт `TMPDIR=/work/tmp`.

При нормальном завершении, ошибке и отмене код пытается удалить репозиторий и отчёты в `finally`. Ошибка удаления логируется, но не меняет успешный результат анализа. При аварийном завершении процесса локальные временные файлы могут остаться; их удаляют после проверки, что они не относятся к активной задаче.

В Compose `/work/tmp` смонтирован как tmpfs и очищается при остановке контейнера. Не меняйте путь репозиториев за пределы разрешённых writable mount: корневая файловая система контейнера read-only.

## Ограничения контейнера

Подготовленный Compose предусматривает:

- непривилегированного пользователя `app`;
- read-only root filesystem;
- снятие capabilities и `no-new-privileges`;
- CPU, memory и PID limits;
- ограниченный tmpfs для временных репозиториев и отчётов;
- отдельный volume для кеша Trivy;
- публикацию порта только на `127.0.0.1`.

Параметры меняются в `compose.yaml`. Это защита в глубину, не гарантия безопасности. API и сканеры по-прежнему используют один контейнер. Кеш Trivy не имеет жёсткой дисковой квоты, а сетевой доступ не ограничен только allowlist-хостами.

Tmpfs расходует оперативную память; повышение лимита временного диска должно учитывать `mem_limit` и память анализаторов. При нехватке памяти возможен OOM, завершение контейнера и потеря состояния API.

## Полезные команды

```powershell
# Состояние сервиса
docker compose ps

# Логи
docker compose logs --tail 100 api
docker compose logs -f api

# Проверка установленных инструментов
docker compose exec api git --version
docker compose exec api gitleaks version
docker compose exec api trivy --version

# Сборка с подробным выводом
docker compose --progress plain build api

# Применение новой конфигурации
docker compose up -d

# Остановка
docker compose down
```

## Что записывается в лог

HTTP middleware фиксирует метод, путь без query string, итоговый HTTP-статус, длительность и `TraceId`. Фоновые логи фиксируют ID задачи, запуск и завершение анализаторов, количество находок, отмену и ошибки.

Лог содержит ошибки процессов и технические пути при исключениях. Не считайте весь поток логов автоматически очищенным от любой чувствительной информации: не включайте debug-дампы инструментов без проверки и не передавайте секреты в URL.

В консоль не записывается полное тело каждого запроса. Логирование не является аудит-базой данных. Долговременное хранение и ротацию настройте отдельно; отсутствие постоянного хранилища задач не требует отсутствия эксплуатационных логов.

Логи сторонних middleware ASP.NET и собственный middleware могут создавать несколько сообщений об одном запросе. Это не означает повторного выполнения сканирования.

## Диагностика

### Docker не находит Dockerfile

Проверьте имя: **`Dockerfile`**, не `.Dockerfile` и не `Dockerfile.txt`. Он должен находиться относительно `build.context` из Compose.

### CLI найден по полному пути, но не по имени

Добавьте в `PATH` каталог, а не сам `.exe`. Проверьте, что буква диска — латинская `C`, не кириллическая `С`. Перезапустите терминал и VS Code. API наследует окружение процесса, из которого запущен.

```powershell
Get-Command git
Get-Command gitleaks
Get-Command trivy
```

### OptionsValidationException: разрешённые хосты

В `.env` должны находиться отдельные значения:

```dotenv
Repositories__AllowedHosts__0=github.com
Repositories__AllowedHosts__1=gitlab.com
```

Не используйте `https://`, путь, список через запятую или wildcard. Локально проверьте расположение `.env` и текущую рабочую папку. Существующая переменная окружения может перекрыть файл из-за `NoClobber()`.

### Swagger возвращает 404

Swagger подключён только в `Development`. Проверьте `ASPNETCORE_ENVIRONMENT`, внешний порт и адрес `/swagger`. В другом окружении корень `/` всё равно перенаправляет на Swagger, но сам UI может быть отключён.

### API_PORT изменён, но порт прежний

`API_PORT` используется Compose. Измените `.env` и выполните `docker compose up -d`. Для локального `dotnet run` используйте `--urls` с `--no-launch-profile`. Простого `docker compose restart` недостаточно для новых переменных.

### Задача получает Failed

Найдите её ID в логах. Возможные причины:

- отсутствует CLI или права на его запуск;
- репозиторий не существует, приватный, перемещён или недоступен без redirect;
- ошибка TLS, DNS, прокси или сети;
- база Trivy не скачалась;
- превышен тайм-аут, размер отчёта, память или временный диск;
- JSON CLI изменился и не соответствует модели адаптера.

Ошибка сканирования не обязана давать HTTP 500: GET существующей задачи вернёт `200`, `status: Failed` и сообщение в `error`.

### Completed, но findings пустой

Проверьте логи каждого адаптера. Затем вручную запустите тот же инструмент над контролируемым набором файлов. Для Trivy убедитесь, что распознаны поддерживаемые dependency/lock-файлы. API не собирает проект и не выполняет `dotnet restore` скачанного репозитория. Ноль находок не равен доказанной безопасности.

### Очередь заполнена

Ответ `429` означает, что свободного места в Channel нет. Повторите позднее или увеличьте вместимость, учитывая ресурсные ограничения. Заголовок Retry-After и автоматический retry сейчас не реализованы.

Отмена ожидающей задачи меняет её статус, но её ID удаляется из очереди только после чтения обработчиком. Поэтому сразу после отмены новый POST всё ещё может получить `429`.

### Отмена вернула true, но задача ещё работает

Ответ подтверждает запрос. Наблюдайте `status` через GET. Выполняющийся код должен передавать токен отмены во все длительные операции. Настоящий CLI проверяется отдельным smoke-тестом; вызов `Cancel()` сам по себе не доказывает остановку любого внешнего приложения.

### После перезапуска всё пропало

Это требование задания. In-memory repository и очередь не восстанавливаются. Кеш Trivy не восстанавливает задачи и результаты. Результаты, которые нужны надолго, клиент должен сохранить самостоятельно.

## Проверка перед передачей проекта

- [ ] В репозитории есть Dockerfile, `.dockerignore`, `compose.yaml`, `.env.example`, README, `docs/` и тесты.
- [ ] В примере окружения стоят конкретные проверенные версии инструментов.
- [ ] `.env`, токены, `bin`, `obj` и результаты сканирования не отслеживаются Git.
- [ ] Запуск из чистого клона повторяется по README.
- [ ] Все автоматические тесты проходят.
- [ ] Настоящие инструменты обнаруживают ожидаемые фиктивные находки.
- [ ] Отмена проверена в очереди, при клонировании и при работе анализатора.
- [ ] При отказе CLI и заполнении очереди нет потерянных зависших задач.
- [ ] После обработки удаляются временные файлы; после рестарта состояние API пустое.
- [ ] GitHub доступен проверяющему; файл с ФИО и ссылкой приложен.
